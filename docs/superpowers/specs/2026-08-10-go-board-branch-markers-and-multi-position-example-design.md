# Go Board Branch Markers and Multi-Position Example

## Context

The guided Go viewer currently configures BesoGo to display child variations.
BesoGo labels every child move alphabetically, even when a node has only one
child. As a result, after a reader chooses variation A or B, the next ordinary
move is also labelled A. That label is generated by the viewer and is not an
annotation stored in the SGF.

The example draft also needs to demonstrate a realistic article containing
several board snapshots: two positions from one SGF and a third position from a
second SGF.

## Marker behavior

The site wrapper will control BesoGo's automatic variation-marker style without
modifying the pinned vendor files:

- At a node with two or more direct authored children, show BesoGo's A/B (and
  later) board labels and the existing contextual variation buttons.
- At a node with zero or one child, hide automatic variation labels. The last
  move keeps BesoGo's normal last-move marker.
- After selecting A or B, the chosen stone and subsequent linear moves appear
  normally. The contextual buttons may continue to identify the chosen sibling
  at the branch itself.
- Navigating back to the fork or returning to a published fork restores the
  automatic labels.
- Try mode follows the same rule and Return restores the published state.

The wrapper must check the current variant style before changing it so the
editor listener does not create a notification loop. BesoGo's vendored sources,
checksums, and provenance remain unchanged.

## Three-board example

The English draft remains factual and does not invent strategic commentary.
It will contain three independent `go-board` shortcodes:

1. `2026-7-26.sgf` at semantic move 64, the record's first fork.
2. `2026-7-26.sgf` at semantic move 80, a later fork in the same record.
3. `2026-7-26_pro.sgf` at semantic move 36, the second record's first fork.

The new source file at the repository root is 4,770 bytes with SHA-256
`4522758078cf8a367e446f981a2f52d3f9f5a91e75e0dc960da38b7100802363`.
It will be copied byte-for-byte beside the existing SGF in the post bundle.
The loose source remains untouched until the feature branch is integrated.

Each shortcode creates its own editor and controls, so navigation and Try mode
on one board cannot change another. The existing shared SGF loader caches by
resource URL: the first two boards share one request, while the third file is
requested separately. Viewer CSS and JavaScript still appear only once on the
page.

## Draft presentation

The draft will use three short sections:

- **First branching point** introduces the move-64 board.
- **A later position from the same SGF** explains that a record can be embedded
  again and introduces the move-80 board.
- **A position from a second SGF** explains that another bundle-local record can
  be embedded and introduces the move-36 board.

Captions identify the record and move. Prose describes only the mechanics of
the example, leaving actual Go analysis for later authoring.

## Performance policy

The current network footprint is already appropriately small and conditional:
posts without a `go-board` shortcode receive no viewer assets, while a viewer
page receives one fingerprinted CSS file and one fingerprinted JavaScript file.
The shared URL-keyed promise cache means the three-board example makes two SGF
requests, not three. Parsing these small records is negligible and parsed-tree
caching would add mutable-state risk without a useful payoff.

Eager board construction is the material cost. A 19×19 BesoGo board creates 361
pointer targets and roughly 566–612 SVG subtree nodes with about 1,085 event
listeners. Mounting all three example boards immediately would create about
1,774 nodes and 3,255 listeners even when the later boards are below the
viewport.

The wrapper will therefore use `IntersectionObserver` to mount a board only
when it enters a 400-pixel vertical margin around the viewport. It will
unobserve the figure before mounting and guard against duplicate mounts. If the
API is unavailable, all boards mount eagerly so functionality is preserved.
No vendor code changes are required.

The server-rendered board host will reserve its square aspect ratio and full
available width before JavaScript mounts BesoGo. Loading and failure status will
overlay that reserved area, preventing the board from shifting the surrounding
article when it initializes.

The follow-up adopts these build budgets, which leave modest headroom over the
measured implementation:

- viewer JavaScript: at most 32,000 bytes minified and 11,000 bytes gzip;
- viewer CSS: at most 5,000 bytes minified and 1,500 bytes gzip;
- combined viewer assets: at most 12,500 bytes gzip.

These budgets apply only to the conditional viewer assets. SGF files remain
ordinary page resources and are fetched only when their board approaches the
viewport.

## Validation

Test-first coverage will establish:

- a real fork enables automatic board labels;
- selecting a branch hides automatic labels on its linear continuation;
- Previous and Return restore labels at a published fork;
- the draft renders exactly three uniquely identified boards with selectors
  64, 80, and 36;
- the first two boards use the same local SGF URL and the third uses the new
  local SGF URL;
- both tracked SGFs match their supplied byte checksums;
- an offscreen board performs no fetch or BesoGo mount before observer
  intersection, mounts exactly once after intersection, and falls back to eager
  mounting without `IntersectionObserver`;
- mounting all three boards produces three independent SVGs and only two SGF
  requests, while an unvisited third board does not fetch the second SGF;
- the server-rendered host reserves a stable square before and after mount;
- minified and gzip viewer assets remain within the stated budgets;
- conditional assets remain single, self-hosted, fingerprinted, and valid at
  both root and project-subpath builds.

Focused tests will be followed by the full Python and Node suites, interaction
ID validation, strict Hugo builds, and `check_site`.

## Out of scope

This follow-up does not add authoring tools, persisted reader variations,
move-level multi-user comments, strategic Go commentary, or changes to the
pinned BesoGo implementation.
